# GitHub Issues Triage 仕様

## 状態

この文書は承認済み仕様である。Ready 追加は2026-10-02にユーザー承認済み。実装済みで、実端末の表示・操作確認は未実施。

## CLI

```text
gh-issues-triage <owner>/<repo>
gh-issues-triage config set-root <absolute-directory>
gh-issues-triage --help
```

- `--help` 単独では Cargo package version、使い方、各引数の説明を標準出力へ表示し、終了コード `0` とする。
- 引数なし、未知のサブコマンド、または `<owner>/<repo>` として解釈できない値は usage を標準エラー出力へ表示し、終了コード `2` とする。
- `owner` と `repo` は空文字を許可しない。余分なパス要素を許可しない。
- 成功時は終了コード `0`、入力・認証・通信・応答・保存・表示の失敗時は非ゼロとする。

## 認証

1. 保存済み access token が有効なら、Issue の取得にそのまま使用する。旧版が保存した access token 単体の値も読み取る。
2. access token が失効した場合、保存済み refresh token があれば `POST https://github.com/login/oauth/access_token` に `client_id`、`grant_type=refresh_token`、`refresh_token` を送り、token を更新する。Device Flow で発行した token のため client secret は使用しない。
3. 更新後の access token と refresh token を組として OS の資格情報ストアへ保存し、新しい access token で Issue 取得を再試行する。
4. 認証情報が未保存、refresh token がない、または GitHub が `bad_refresh_token` を返した場合だけ Device Flow を開始する。資格情報ストアや通信の失敗、その他の更新エラー、repository の権限不足は理由を示して失敗終了する。
5. Device Flow では、GitHub App の client ID を `GITHUB_CLIENT_ID` 環境変数から読み込む。未設定または空の場合は失敗する。
6. `POST https://github.com/login/device/code` で `device_code`、`user_code`、`verification_uri`、`expires_in`、`interval` を取得する。
7. `verification_uri` と `user_code` を表示する。ブラウザの自動起動は行わない。
8. GitHub が返した `interval` 以上の間隔で `POST https://github.com/login/oauth/access_token` をポーリングする。
9. `authorization_pending` は待機を継続し、`slow_down` は GitHub の指示どおり待機間隔を延長する。
10. 成功時だけ access token と、発行された場合の refresh token を資格情報ストアへ保存し、Issue 取得を続ける。拒否、期限切れ、不正な client ID、Device Flow 無効化、通信失敗は理由を示して失敗終了する。

`GITHUB_CLIENT_ID` は token 更新または Device Flow が必要になったときに読み込む。

## `<owner>/<repo>`

### Issue の取得

- GitHub REST API の `GET /repos/{owner}/{repo}/issues` を使用する。
- `state=open`、`sort=created`、`direction=desc` とする。
- REST API が返す `pull_request` フィールド付き項目を除外する。
- 除外後に10件へ達するまで必要なページを読み、リポジトリに存在する open Issue が10件未満なら存在する件数だけを対象とする。
- triage に使用する GitHub の値は `number`、`title`、`body` とする。`body: null` は本文なしとして扱う。

「最新」は `created_at` の降順とする。

### Jev による重要度

- TypeSafe HTTP API `POST https://api.typesafe.ai/v1/systemone` を `Authorization: Bearer <API_KEY>` 付きで使用する。
- model は追従用エイリアス `jev-latest` とする。
- 10件を1つの構造化 `state` にまとめ、Issue ごとに独立した `Score` question を1つ作る。
- 各 question の instructions は、対象 Issue の `number`、`title`、`body` のパスと、重要度を判定することを明記する。question ID 自体には意味を依存させない。
- Score は次の5段階を低い順に使用する。

| level | 基準 |
| ---: | --- |
| 0 | 対応不要、情報提供のみ、または影響が確認できない |
| 1 | 影響が小さく、容易な回避策がある |
| 2 | 通常機能に影響するが、業務を止めない |
| 3 | 主要機能を妨げる、広い利用者に影響する、または回避が困難 |
| 4 | データ損失、セキュリティ、サービス停止など直ちに対応すべき影響 |

- API が返す確率加重 `score` を検証し、変換せず重要度として使用する。
- `confidence` は順位計算に使わず、初期版では表示しない。
- 一部でも回答が欠ける、不正な型である、または TypeSafe が失敗した場合は、推測値で補わずコマンド全体を失敗させる。
- `429` と `529` は上限付きの指数バックオフで再試行し、上限到達後は失敗させる。具体的な回数とタイムアウトは実装時にテスト可能な定数として決める。

### 並べ替え

- 重要度を降順に安定ソートする。
- 同じ重要度では GitHub から取得した順序を維持する。

## テーブル

```text
┌────────┬───────┬──────┬──────────────────────────────────────┐
│ 重要度 │ Ready │ 番号 │ Issues                               │
├────────┼───────┼──────┼──────────────────────────────────────┤
│ 3.6    │ Yes   │ #42  │ Issue のタイトル                     │
│        │       │      │ Issue の内容                         │
└────────┴───────┴──────┴──────────────────────────────────────┘
```

- 出力先が端末であり幅を取得できる場合、各行の表示幅をその端末幅と一致させる。
- 固定列は内容と左右 padding が収まる最小幅とし、残りを `Issues` 列へ割り当てる。
- `Issues` 列ではタイトル、その直後の行から本文を表示する。入力中の改行を保持し、各行を列幅で折り返す。
- 折り返しは Unicode の端末表示幅を基準にし、セル境界を越えない。
- Issue ごとに中罫線を置く。
- 端末幅を取得できない場合、または4列を成立させる幅がない場合は理由を示して失敗する。根拠のない既定幅へ置き換えない。
- 対象 Issue が0件の場合はヘッダーだけを持つ空テーブルを表示して成功終了する。

### 一覧の仮選択とスクロール

- マウスオーバーした Issue を仮選択する。ヘッダー・横罫線・ヘルプなど Issue の行範囲外へ移動すると選択を解除する。
- `j`・下矢印で次の Issue、`k`・上矢印で前の Issue を仮選択する。先頭・末尾では停止し、折り返さない。
- 選択がない状態の初回キー操作では、先頭の表示 Issue を選択する。Issue がまだ表示されていない場合は先頭の Issue を選択する。
- 最後のマウス移動または仮選択キー操作を優先する。マウスオーバー後のキー操作は、その Issue を基準に次／前へ移動する。
- 選択した Issue が画面外なら自動スクロールする。画面より高い Issue は、選択時にその先頭が見える位置へ移動する。
- PageUp/PageDown は表示領域の行数分スクロールし、上下端では停止する。選択状態は維持する。
- 仮選択した Issue の全セルに、余白・タイトル・本文・ブランチ作成ボタンを含めて背景 bright blue（SGR `104`）、文字 black（SGR `30`）を適用する。ANSI 16色を使い、実際の色味は端末パレットに従う。
- 縦罫線の前で前景・背景を既定色へ戻す。外枠・縦罫線・横罫線・ヘッダー・ヘルプの色は変えない。
- 仮選択だけではブランチ作成を実行しない。ブランチ作成結果の画面では、`j`/`k`・上下矢印は従来どおり1行ずつスクロールする。

## 設定と秘密情報

- `TYPESAFE_API_KEY` は環境変数から取得し、永続保存しない。
- GitHub App client ID は `GITHUB_CLIENT_ID` 環境変数から取得する。client secret と PAT は使用しない。
- GitHub App user access token と、発行された場合の refresh token はサービス名 `gh-issues-triage`、アカウント名 `github.com` で OS の資格情報ストアへ保存する。
- macOS では Keychain、Linux では Secret Service を使用する。利用不能時は失敗し、平文ファイルへ fallback しない。
- 秘密情報をエラー本文へ含めない。

## 対象

- サービスは GitHub.com に限定する。
- OS は macOS と Linux に対応する。
- GitHub App とユーザーの権限でアクセスできる public/private repository を対象とする。

## 追加仕様: ブランチ作成

- 既存の重要度 `Score` 判定に加え、同じ Issue の `number`、`title`、`body` を参照する独立した Jev `Choice` question で `refactor` / `fix` / `feat` / `chore` / `docs` の一つを選ぶ。既存の最大10件・重要度順は維持する。
- `Choice` の回答は質問数、型、選択肢を検証する。不完全・不正な回答に既定の prefix を当てず、トリアージを失敗させる。
- Issue 番号を十進数で表し、`<prefix>/issue-<number>` をブランチ名とする。Issue タイトルの翻訳・要約や追加の生成 API は使用しない。
- `gh-issues-triage config set-root <directory>` で既存の絶対パスを root として保存する。設定先は `XDG_CONFIG_HOME/gh-issues-triage/config.json`、未設定時は `~/.config/gh-issues-triage/config.json` とする。設定値は公開パスであり token や API key は保存しない。
- CLI 引数 `<owner>/<repo>` の `repo` をローカルディレクトリ名とし、`root/repo` を対象にする。root 未設定・候補パス不在の場合はブランチ作成を拒否する。候補パスが指定されたリポジトリに対応するかを検証してから Git 操作を行う。
- ブランチの起点は対象ローカルリポジトリの `main`。`main` がない場合、別の ref を代用しない。同名ブランチがある場合、上書きしない。
- 各 Issue の本文の下にブランチ名とマウスでクリックできる作成ボタンを表示する。クリック後にブランチを作成する。端末はクリックを受け取る間、対話状態を維持する。キーボードでは `1`〜`9`・`0`（10件目）で対応する Issue のブランチを作成する。
- 作成時に対象リポジトリを新しいブランチへ切り替え、CLI の作業ディレクトリは変更しない。対象リポジトリを明示して Git 操作を実行する。クリック前にブランチを作成しない。
- ディレクトリ・Git・Jev のエラーは理由を表示し、成功表示しない。`repo` をシェル文字列へ直接埋め込まない。

## 追加仕様: ブランチ状態の表示

表示位置・記号・凡例は2026-10-01にユーザー承認済み。2026-10-01に実装済み。実端末での表示確認は未実施。以下の照合範囲と確認方法は、承認済みの表示を実装するための補足仕様とする。

### 表示

- `重要度`、`Ready`、`番号`、`Issues` の4列構成とし、各 Issue の先頭行の番号右隣に状態を表示する。
- 番号の最大表示幅に合わせて番号部分を空白で埋め、その後に半角空白1文字と状態の領域を置く。状態の位置は全 Issue で揃える。
- 状態は、ブランチありを `🌿`、ブランチなしを空欄、確認不能を `?` とする。状態の領域は `🌿` の Unicode 表示幅とし、空欄と `?` の余白を同じ幅に揃える。
- 番号列は状態と padding を含めて幅を計算し、残りを `Issues` 列へ割り当てる。端末幅不足の扱いは既存のテーブル仕様に従う。
- Issue が1件以上ある場合、一覧のヘルプに論理1行の凡例 `🌿 ブランチあり / 空欄 ブランチなし / ? 確認不能` を表示する。端末幅に収まらない場合は既存の折り返し処理で表示する。0件の場合は従来どおりヘッダーだけを表示する。
- 状態にも番号セルと同じ仮選択ハイライトを適用する。凡例は Issue の選択領域に含めない。

### 照合と確認不能

- 一覧表示前に一度、保存済み root と CLI の `repo` から対象ローカルリポジトリを解決する。Git root と origin が CLI の `<owner>/<repo>` に一致することを、既存の対象検証と同じ規則で確認する。
- ローカルブランチ `refs/heads/<prefix>/issue-<number>` の存在を確認する。`prefix` は既存の許可値 `refactor` / `fix` / `feat` / `chore` / `docs` のいずれかとし、Issue 番号は完全一致で照合する。
- 今回の Jev 分類と異なる許可 prefix でも、同じ Issue 番号のローカルブランチがあれば `🌿` とする。独自命名のブランチ、remote-tracking ref、リモート上だけのブランチは照合対象に含めない。
- 判定は現在の存在状態を示す。削除済みブランチの作成履歴や、一覧表示後の外部操作による変更は追跡しない。
- この画面でブランチ作成に成功した場合は、結果画面から一覧へ戻る際に状態を再確認し、番号右隣の表示と確認不能の理由を更新する。仮選択は維持し、スクロール位置は表示領域に収まるよう補正する。
- 存在確認には `main` の存在を要求しない。`main` の検証は従来どおりブランチ作成時に行う。
- root 未設定、設定の読込失敗、対象パス不在、対象リポジトリ不一致、Git の確認失敗では `?` とし、確認できなかった理由を表示する。共通の原因は1回表示し、確認失敗をブランチなしへ置き換えない。
- ブランチ状態の確認失敗だけでは一覧表示を中止せず、終了コードも失敗にしない。認証・Issue 取得・Jev・端末表示・ブランチ作成の失敗は従来のエラー仕様に従う。
- 確認は読み取り専用とし、ブランチ作成・切り替え・fetch・push は行わない。既存の作成対象名、ボタン、キーボード操作、作成結果画面は維持する。

## 追加仕様: 着手可能度（Ready）

### Jev の入力と出力

- 既存の構造化 `state` と1回の Jev リクエストを利用し、Issue ごとに独立した `Choice` question を1つ追加する。重要度 `Score` とブランチ分類 `Choice` の結果は判定材料にしない。
- instructions に対象 Issue の `number`、`title`、`body` のパスを明記し、要求の具体性、必要な再現条件、完了条件、着手前の追加調査を評価させる。
- 選択肢は `Yes`、`Needs information`、`Needs investigation` の3つとし、検証済みの選択結果をそのまま表示する。4観点を個別の回答や追加列として返させない。
- 判定はタイトルと本文に記載された情報に限定する。存在しない再現条件や完了条件を推測して補わず、コードや実環境を調査済みと扱わない。
- 本文なしは引き続き有効な入力として判定する。タイトルだけで十分かを評価し、本文がないこと自体を API エラーとしない。Issue が0件なら従来どおり Jev を呼ばない。

| 値 | 判定基準 |
| --- | --- |
| `Yes` | 要求と完了条件が明確で、必要な再現条件があり、実装への着手を妨げる情報不足・事前調査がない |
| `Needs information` | 要求、完了条件、必要な再現条件などが不足し、報告者や依頼者からの追加情報が必要 |
| `Needs investigation` | 要求と完了条件、必要な再現条件は十分だが、実装に先立つ原因・影響範囲・実現可能性などの技術調査が必要 |

- 情報不足と技術調査が併存する場合は `Needs information` を選ぶ。
- 再現条件は不具合など再現が必要な Issue に適用する。機能追加や文書変更などに再現手順がないことだけを理由に `Needs information` としない。
- 通常の実装中に行うコード確認や実装方法の選択だけでは `Needs investigation` としない。原因が未特定という記述だけでも一律には判定せず、着手前の調査が必要かを評価する。
- 例: 期待する動作が不明な不具合は `Needs information`、再現条件と期待する動作が明確でも原因調査を先に要する不具合は `Needs investigation`、変更内容と完了条件が具体的な文書修正は `Yes`。
- 回答の件数、質問との対応、型、選択肢を既存の `Choice` と同様に検証する。欠落・不正・API 失敗はトリアージ全体を失敗させ、3つの Ready 値で通信や検証の失敗を表さない。
- 既存の `Choice` と同じく confidence と確率の型・範囲、確率キーの一致・合計、選択値が最大確率であることも検証する。HTTP timeout と上限付き再試行は既存の規則を維持する。
- 確率や confidence を表示せず、独自の閾値やスコア変換を追加しない。Ready は重要度順の安定ソートに使用しない。

### テーブルと操作

- 既存の3列構成を `重要度`、`Ready`、`番号`、`Issues` の4列構成へ変更する。番号右隣のブランチ状態は維持する。
- Ready は上寄せ・左寄せで、各 Issue の先頭行に値全体を表示し、後続行は空欄とする。省略や略記はしない。
- Ready 列の内容幅は、ヘッダーと当該一覧の判定文字列の最大 Unicode 表示幅とする。左右 padding は既存の列と同じ規則を使用し、残りの幅を `Issues` 列へ割り当てる。
- 4列と `Issues` の表示に必要な最小幅を確保できない場合、既存の幅不足エラーとして理由を示して失敗する。0件の場合も `Ready` を含むヘッダーだけの空テーブルを表示する。
- Ready セルの値と余白にも既存の仮選択ハイライトを適用し、罫線は装飾しない。列追加後のクリック領域と Issue の物理行範囲は描画結果に合わせる。
- Ready は参照情報とし、ブランチ作成を禁止したり、追加確認を求めたりしない。判定結果は永続保存せず、一覧内での再判定やポーリングも追加しない。
