# GitHub Issues Triage 要求定義

## 文書の読み方

要求と受け入れ条件は、個別の表記がなければ必須（MUST）とする。
目的、用語の説明、承認状態、検証記録は要求レベルの対象外とする。
条件を示す接続表現は「場合」に統一する。

| 要求レベル | 意味 |
| --- | --- |
| 必須（MUST） | 実装または検証が満たす要求 |
| 推奨（SHOULD） | 例外の理由を示す場合に限り省略できる要求 |
| 任意（MAY） | 実装者が採用を選択できる許可事項 |

## 用語集

| 用語 | 意味 |
| --- | --- |
| アプリケーション | `gh-issues-triage` の実行プログラム |
| ユーザー | アプリケーションを操作する人 |
| Issue | GitHub の Issue。プルリクエストは含まない |
| open 状態の Issue | GitHub の `state=open` に該当する Issue |
| トリアージ | Issue の取得、Jev の判定、並べ替え、一覧表示 |
| 重要度 | Jev の検証済み `score` の値 |
| Ready | Issue の記述に基づく着手可能度 |
| ブランチ分類 | Jev が選ぶブランチ名の `prefix` |
| アクセストークン | GitHub App user access token |
| リフレッシュトークン | アクセストークンの更新に使用する refresh token |
| クライアント ID | GitHub App の client ID |
| クライアントシークレット | GitHub App の client secret |
| 認証情報 | 保存対象のアクセストークンとリフレッシュトークン |
| Device Flow | GitHub App のデバイス認証手順 |
| 資格情報ストア | OS が提供する秘密情報の保存先 |
| プロジェクトルート | ローカルプロジェクト群の親ディレクトリ `root` |
| 対象リポジトリ | CLI の `<owner>/<repo>` で指定した GitHub リポジトリ |
| 対象ローカルリポジトリ | プロジェクトルート配下の `root/repo` |
| ブランチあり | 許可した名前のローカルブランチが存在する状態 |
| ブランチなし | 許可した名前のローカルブランチが存在しない状態 |
| 確認不能 | ローカルブランチの有無を確認できない状態 |
| 仮選択 | ブランチを作成せずに Issue を選ぶ操作 |
| 表示領域 | 一覧または結果を画面内に表示できる領域 |
| 余白 | セル内で内容と罫線の間に置く空白。padding に相当 |
| Unicode 表示幅 | Unicode 文字が端末上で占める幅 |
| 質問 | Jev API の question |
| 判定指示 | Jev API の instructions |
| 構造化状態 | Jev API の `state` |
| 事前調査 | 実装への着手前に行う原因、影響範囲、実現可能性などの調査 |
| 成功終了 | 終了コード `0` での終了 |
| 失敗終了 | 非ゼロの終了コードでの終了 |
| 代替手段 | 本来の処理を別の処理で置き換える fallback |

## 変更案の状態

ユーザーは2026-10-02に Ready の追加要求を承認した。
Ready の追加要求は実装済みである。
実端末での Ready の表示確認は未実施である。
実端末での Ready の操作確認は未実施である。
文書の書き直しは、他の要求の承認状態を変更しない。

## 目的

アプリケーションは、対象リポジトリの直近の Issue を端末に表示する。
アプリケーションは、人が最初に確認すべき順に Issue を並べる。

## 対象ユーザー

- 対象ユーザーは、CLI から Issue を短時間で確認したい開発者とする。

## 機能要求

### 認証

実行コマンドは次の形式とする。

```text
gh-issues-triage <owner>/<repo>
```

- 保存済みアクセストークンが有効な場合、アプリケーションはアクセストークンを使用する。
- アクセストークンが失効した場合、アプリケーションはアクセストークンを自動更新する。
- アクセストークンの更新には、アプリケーションは保存済みリフレッシュトークンを使用する。
- 次の条件のいずれかを満たす場合だけ、アプリケーションは Device Flow を開始する。
  - アプリケーションの認証情報が未保存である。
  - アプリケーションのリフレッシュトークンが存在しない。
  - アプリケーションのリフレッシュトークンが失効している。
- Device Flow 中、アプリケーションは確認 URL を表示する。
- Device Flow 中、アプリケーションはユーザーコードを表示する。
- アプリケーションは、ユーザーによるブラウザ認証の完了を待つ。
- 認証または更新が成功した場合、アプリケーションは認証情報を保存する。
- 認証情報の保存後、アプリケーションは Issue の取得を続ける。
- 後続の実行では、アプリケーションは保存済み認証情報を利用できる。
- アプリケーションは、環境変数 `GITHUB_CLIENT_ID` からクライアント ID を取得する。
- アプリケーションは、アクセストークンを資格情報ストアへ保存する。
- リフレッシュトークンの発行後、アプリケーションはリフレッシュトークンを資格情報ストアへ保存する。
- アプリケーションは、PAT を使用しない。
- アプリケーションは、資格情報ストアの代替手段として平文ファイルを使用しない。
- アプリケーションは、クライアントシークレットを配布物へ保存しない。
- アプリケーションは、クライアントシークレットをローカル設定へ保存しない。

### トリアージ

- アプリケーションは、対象リポジトリの open 状態の Issue を新しい順に取得する。
- アプリケーションが取得する Issue は、最大10件とする。
- アプリケーションは、プルリクエストを取得対象に含めない。
- アプリケーションは、Issue のタイトルと本文を Jev の `Score` プリミティブへ渡す。
- Jev は、Issue の重要度を算出する。
- アプリケーションは、検証済みの `score` を重要度として使用する。
- アプリケーションは、検証済みの `score` を変換しない。
- アプリケーションは、重要度の降順で Issue を表示する。
- Issue の表示後、アプリケーションは終了する。
- 重要度が同じ場合、アプリケーションは取得時の新しい順を維持する。

### 表示

- アプリケーションは、結果を罫線付きテーブルで表示する。
- テーブルの列順は、`重要度`、`Ready`、`番号`、`Issues` とする。
- アプリケーションは、テーブル全体の表示幅を実行時の端末幅に合わせる。
- アプリケーションは、各セルの内容を上寄せにする。
- アプリケーションは、各セルの内容を左寄せにする。
- アプリケーションは、内部の縦罫線 `│` の左右に半角空白を1文字ずつ置く。
- 外枠は、縦罫線の左右の空白に関する要求の対象外とする。
- アプリケーションは、タイトルを本文より先に表示する。
- アプリケーションは、本文をタイトルと同じセル内で折り返す。
- Issue が複数行の場合、アプリケーションは重要度を先頭行だけに表示する。
- Issue が複数行の場合、アプリケーションは Ready を先頭行だけに表示する。
- Issue が複数行の場合、アプリケーションは番号を先頭行だけに表示する。
- アプリケーションは、番号の右隣にブランチ状態を表示する。
- ブランチありの場合、アプリケーションは `🌿` を表示する。
- ブランチなしの場合、アプリケーションは `🌿` と同じ表示幅の空欄を表示する。
- 確認不能の場合、アプリケーションは `?` を表示する。
- アプリケーションは、全 Issue でブランチ状態の表示位置を揃える。
- アプリケーションは、一覧にブランチ状態の凡例を1行表示する。
- 確認不能の場合、アプリケーションは確認不能の理由を表示する。
- 確認不能の場合、アプリケーションは一覧表示を継続する。
- アプリケーションは、確認不能をブランチなしとして扱わない。
- ユーザーは、マウスオーバーで Issue を仮選択できる。
- ユーザーは、`j`、`k`、上下矢印で Issue 単位の仮選択を行える。
- アプリケーションは、仮選択に ANSI 16色の bright blue 背景を適用する。
- アプリケーションは、仮選択の文字を黒にする。
- アプリケーションは、仮選択の余白もハイライトする。
- アプリケーションは、仮選択で罫線の色を変えない。
- 仮選択した Issue が画面外の場合、アプリケーションは一覧を自動スクロールする。
- ユーザーは、PageUp と PageDown で画面単位のスクロールを行える。
- ユーザーは、画面単位のスクロールで長い本文を閲覧できる。

## 品質要求

- アプリケーションは、GitHub の失敗を成功として扱わない。
- アプリケーションは、TypeSafe の失敗を成功として扱わない。
- アプリケーションは、認証情報の保存失敗を成功として扱わない。
- GitHub、TypeSafe、認証情報保存の失敗では、アプリケーションは原因を標準エラー出力へ示す。
- GitHub、TypeSafe、認証情報保存の失敗では、アプリケーションは非ゼロで終了する。
- アプリケーションは、次の秘密情報をログや結果テーブルへ出力しない。
  - GitHub と TypeSafe の API キー
  - アクセストークン
  - デバイスコード
- アプリケーションは、API のタイムアウト後に無期限で待機しない。
- アプリケーションは、API のレート制限後に無期限で待機しない。
- アプリケーションは、タイトルと本文の幅を Unicode 表示幅で計算する。
- 日本語、絵文字、全角文字も、Unicode 表示幅による計算の対象とする。
- アプリケーションは、タイトルと本文の表示幅にバイト数を使用しない。

## 受け入れ条件

- 認証情報が未保存の場合、ユーザーは対象リポジトリの指定から認証を開始できる。
- ユーザーは、Device Flow の案内に従って認証を完了できる。
- 認証成功後、アプリケーションは認証情報を保存できる。
- 認証情報の保存後、アプリケーションは Issue を表示できる。
- アクセストークンが有効な場合、アプリケーションは保存済みアクセストークンを使用する。
- アクセストークンが有効な場合、アプリケーションは再認証しない。
- アクセストークンが失効した場合、アプリケーションはアクセストークンを更新できる。
- アクセストークンの更新には、アプリケーションはリフレッシュトークンを使用する。
- リフレッシュトークンが存在しないか失効した場合だけ、アプリケーションは認証を開始する。
- リフレッシュトークンが使用できない場合の認証方式は、Device Flow とする。
- 認証済みの場合、アプリケーションは最大10件の open 状態の Issue を表示する。
- アプリケーションは、取得した Issue を重要度順に表示する。
- プルリクエストが混在する場合も、アプリケーションは Issue だけを表示する。
- テーブルは、表示要求の幅、配置、余白、折り返しを満たす。
- 全 Issue が一画面に収まる場合も、ユーザーはキー操作で各 Issue を仮選択できる。
- ユーザーは、マウスオーバーからキー操作へ切り替えられる。
- 仮選択のハイライトは、タイトル、本文、ボタンに適用される。
- 仮選択のハイライトは、罫線や他の Issue の色を変えない。
- アプリケーションは、仮選択だけでブランチを作成しない。
- GitHub または TypeSafe が失敗した場合、アプリケーションは不完全な順位表を成功表示しない。

## 制約

- アプリケーションの実装言語は Rust とする。
- アプリケーションの HTTP クライアントは `reqwest` とする。
- アプリケーションは、GitHub の公式 API を使用する。
- 重要度判定には、アプリケーションは TypeSafe Jev の `Score` プリミティブを使用する。

## 追加要求: Issue からのブランチ作成

- アプリケーションは、各 Issue の本文下にブランチ作成ボタンを配置する。
- ユーザーは、ブランチ作成ボタンをマウスでクリックできる。
- Jev は、各 Issue に次のブランチ分類のいずれかを選ぶ。
  - `refactor`
  - `fix`
  - `feat`
  - `chore`
  - `docs`
- アプリケーションは、ブランチ分類をブランチ名の `prefix` に使用する。
- アプリケーションは、Issue 番号から `issue-<number>` を作る。
- アプリケーションは、`issue-<number>` をブランチ名の後半に使用する。
- ユーザーは、プロジェクトルートを設定できる。
- アプリケーションは、プロジェクトルートを設定ファイルへ保存する。
- アプリケーションは、CLI の `repo` をローカルディレクトリ名に使用する。
- アプリケーションは、`owner/` をローカルディレクトリ名に含めない。
- アプリケーションは、`root/repo` を対象ローカルリポジトリとする。
- ブランチ名は `<prefix>/issue-<number>` とする。
- アプリケーションは、対象ローカルリポジトリの `main` からブランチを作成する。
- 作成成功後、アプリケーションは対象ローカルリポジトリを新しいブランチへ切り替える。
- アプリケーションは、CLI の作業ディレクトリを変更しない。
- 作成対象が次の状態の場合、アプリケーションは別の場所や名前を暗黙に使用しない。
  - 対象ディレクトリが不正または存在しない。
  - `main` が不正または存在しない。
  - ブランチ名が不正または既存のブランチと競合する。
- アプリケーションは、Git 操作の失敗を成功表示しない。
- アプリケーションは、既存の作業内容を上書きしない。
- アプリケーションは、既存のブランチを上書きしない。

### 追加分の受け入れ条件

- アプリケーションは、各 Issue の本文下に作成対象のブランチ名を表示する。
- アプリケーションは、各 Issue の本文下にクリック可能な作成ボタンを表示する。
- ユーザーは、クリックした Issue のブランチだけを作成できる。
- 作成したブランチの起点は、対象ローカルリポジトリの `main` とする。
- 作成したブランチ名は、`<prefix>/issue-<number>` に一致する。
- タイトルの言語にかかわらず、アプリケーションは Issue 番号からブランチ名の後半を作れる。
- 次の失敗が発生した場合、アプリケーションは失敗をユーザーへ知らせる。
  - 対象ディレクトリが存在しない。
  - Git リポジトリが指定と一致しない。
  - `main` が存在しない。
  - 同名ブランチが存在する。
  - ブランチ分類の取得が失敗する。
  - Git 操作が失敗する。
- 作成対象の検証や作成処理が失敗した場合、アプリケーションは意図しないブランチを作成しない。
- 次回の起動でも、アプリケーションは保存済みプロジェクトルートを利用できる。
- 作成成功後、対象ローカルリポジトリの現在のブランチは作成したブランチとする。
- 作成成功後も、CLI の作業ディレクトリは変わらない。

## 追加要求: ブランチ状態の表示

ユーザーは2026-10-01に表示位置、記号、凡例を承認した。
ブランチ状態の表示は2026-10-01に実装済みである。
実端末でのブランチ状態の表示確認は未実施である。

- アプリケーションは、対象ローカルリポジトリのブランチを読み取り専用で確認する。
- アプリケーションは、リモート上だけのブランチを確認対象に含めない。
- アプリケーションは、過去のブランチ作成履歴を確認対象に含めない。
- ブランチ状態の表示には、アプリケーションは新しい列を追加しない。
- ブランチ状態の表示には、アプリケーションは新しい設定を追加しない。
- ブランチ状態の表示には、アプリケーションは新しい依存関係を追加しない。
- ブランチ状態の表示は、既存の作成ボタンとキー操作を変更しない。

### 追加分の受け入れ条件: Issue からのブランチ作成

- ユーザーは、番号右隣の `🌿` でブランチありを識別できる。
- ユーザーは、番号右隣の空欄でブランチなしを識別できる。
- ユーザーは、番号右隣の `?` で確認不能を識別できる。
- ユーザーは、凡例でブランチ状態の意味を確認できる。
- アプリケーションは、ブランチ状態を含む番号列の幅を Unicode 表示幅で計算する。
- タイトル、本文、罫線は、端末幅に収まる。
- 次の条件では、アプリケーションは `?` と確認不能の理由を表示する。
  - プロジェクトルートが未設定である。
  - 対象ローカルリポジトリが指定と一致しない。
  - Git による確認が失敗する。
- ブランチ状態が確認不能の場合も、アプリケーションは Issue 一覧を表示できる。
- 状態確認だけでは、アプリケーションは次の操作を実行しない。
  - ブランチ作成
  - ブランチ切り替え
  - fetch
  - push
  - 作業ファイルの変更

## 追加要求: 着手可能度（Ready）

### 目的と範囲

- ユーザーは、Ready で Issue の記述から実装への着手可否を把握できる。
- ユーザーは、重要度とは別に情報不足や事前調査の必要性を把握できる。
- Jev は、次の観点で Ready を判定する。
  - 要求の具体性
  - 必要な再現条件
  - 完了条件
  - 着手前の事前調査の必要性
- Jev は、既存の Issue のタイトルと本文を判定に使用する。
- Ready の判定では、アプリケーションは次の処理を実行しない。
  - コメントの取得
  - コードの調査
  - 実際の再現
  - 追加情報の自動収集
- アプリケーションは、テーブルに `Ready` 列を追加する。
- アプリケーションは、各 Issue に次の値のいずれかを表示する。
  - `Yes`
  - `Needs information`
  - `Needs investigation`
- Ready の追加後も、アプリケーションは重要度の算出方法を維持する。
- Ready の追加後も、アプリケーションは重要度の並べ替え方法を維持する。
- Ready の追加後も、アプリケーションはブランチ分類を維持する。
- Ready の追加後も、アプリケーションはブランチ状態の表示を維持する。
- Ready の追加後も、アプリケーションはブランチ作成操作を維持する。
- アプリケーションは、Ready をブランチ作成の許可条件に使用しない。

### 判定基準

#### `Yes`

- Issue の要求は、実装する変更内容を特定できる内容とする。
- Issue の完了条件は、作業の完了を判定できる内容とする。
- Issue は、必要な再現条件を含む。
- Issue の情報不足は、実装への着手を妨げない。
- Issue は、実装への着手を妨げる事前調査を必要としない。

#### `Needs information`

- Issue は、要求、完了条件、必要な再現条件などの情報が不足している。
- ユーザーは、報告者または依頼者への確認を必要とする。

#### `Needs investigation`

- Issue の要求は、実装する変更内容を特定できる内容とする。
- Issue の完了条件は、作業の完了を判定できる内容とする。
- Issue は、必要な再現条件を含む。
- Issue は、原因、影響範囲、実現可能性などの事前調査を必要とする。

#### 判定の優先順位と例外

- 情報不足と事前調査が併存する場合、Jev は `Needs information` を優先する。
- 不具合以外の Issue には、Jev は再現手順を一律に要求しない。
- `Yes` の判定には、Jev は実装方法の全詳細を要求しない。
- `Yes` の判定には、Jev は原因の特定結果を一律に要求しない。
- 通常の実装中の確認だけで足りる場合、Jev は事前調査が必要と判定しない。

### 受け入れ条件: 着手可能度（Ready）

- Jev は、Ready を重要度から独立して判定する。
- Jev は、Ready をブランチ分類から独立して判定する。
- Ready の値は、重要度順を変えない。
- Ready の値は、同じ重要度の Issue の取得順を変えない。
- アプリケーションは、指定した3つの Ready 値だけを表示する。
- Ready の回答が欠落または不正な場合、アプリケーションは既存の Jev エラー方針に従う。
- アプリケーションは、欠落または不正な回答を Ready の値で置き換えない。
- テーブルの列順は、`重要度`、`Ready`、`番号`、`Issues` とする。
- アプリケーションは、各 Issue の先頭行だけに Ready を表示する。
- Ready の表示は、次の既存仕様を維持する。
  - 端末幅
  - Unicode 表示幅
  - 余白
  - 折り返し
  - 仮選択のハイライト
- 端末幅が不足する場合、アプリケーションは理由を表示する。
- 端末幅が不足する場合、アプリケーションは失敗終了する。
- Ready の値にかかわらず、ユーザーは既存のブランチ状態を確認できる。
- Ready の値にかかわらず、ユーザーは既存のクリック操作を利用できる。
- Ready の値にかかわらず、ユーザーは既存のキー操作を利用できる。

### 未決事項

未決事項は存在しない。
ユーザーは、Ready の判定基準を承認済みである。
ユーザーは、Ready の列位置を承認済みである。
ユーザーは、Ready の判定対象の範囲を承認済みである。
