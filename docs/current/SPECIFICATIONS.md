# GitHub Issues Triage 仕様

## 文書の読み方

本文の動作規則は、すべて必須 (MUST) とする。

## CLI

```text
gh-issues-triage <owner>/<repo>
gh-issues-triage next <owner>/<repo> --format json
gh-issues-triage config set-root <absolute-directory>
gh-issues-triage --help
```

- owner と repo は空でない値とし、空白と余分なパス要素を拒否する。
- `.` と `..` は、owner と repo に指定できない。
- `--help` は、バージョン、使い方、引数説明を表示する。
- 正常終了は `0`、引数不正は `2`、処理失敗は `1` とする。
- 引数不正では、理由と使い方を標準エラー出力へ表示する。

## 認証

### エンドポイント

| 名称 | HTTP メソッドと URL |
| --- | --- |
| デバイスコード取得 | `POST https://github.com/login/device/code` |
| トークン取得・更新 | `POST https://github.com/login/oauth/access_token` |

### 保存済み認証情報の使用と更新

- 保存済みアクセストークンが有効な場合、アプリケーションはアクセストークンを使用する。
- 保存済みアクセストークンの用途は、Issue の取得とする。
- アプリケーションは、アクセストークン単体と、トークンを保持する JSON の両形式を読み取る。
- 次の条件を両方満たす場合、アプリケーションはトークン取得・更新へ更新要求を送る。
  - アクセストークンが失効している。
  - 保存済みリフレッシュトークンが存在する。
- 更新要求のパラメーターは、次の値とする。
  - `client_id`
  - `grant_type=refresh_token`
  - `refresh_token`
- Device Flow のトークン更新では、アプリケーションはクライアントシークレットを使用しない。
- 更新成功後、アプリケーションは2つのトークンを組として資格情報ストアへ保存する。
- 保存成功後、アプリケーションは新しいアクセストークンで Issue 取得を再試行する。

### Device Flow の開始条件

- 次の条件のいずれかを満たす場合だけ、アプリケーションは Device Flow を開始する。
  - アプリケーションの認証情報が未保存である。
  - アプリケーションのリフレッシュトークンが存在しない。
  - GitHub が `bad_refresh_token` を返す。
  - トークン更新時に GitHub が `incorrect_client_credentials` を返す。
- 更新時の `incorrect_client_credentials` は、トークンの失効と断定しない。
- 同エラーでは、アプリケーションは更新時に拒否された旨を表示する。
- 同エラーでは、アプリケーションは再認証が必要である旨を表示する。
- 認証案内は、一覧では標準出力、`next` では標準エラー出力へ出す。
- アプリケーションは、Device Flow を一度だけ開始する。
- Device Flow 自体が失敗した場合、アプリケーションは失敗終了する。
- Device Flow の再認証では、GitHub の応答の待機間隔と有効期限を使用する。
- 再認証成功後だけ、アプリケーションは新しい認証情報を保存する。
- 再認証前に、アプリケーションは保存項目を削除しない。
- 保存成功後、アプリケーションは Issue 取得を一度だけ再試行する。
- 再取得が失敗した場合、アプリケーションは再認証を繰り返さない。
- Device Flow へ進まない認証エラーは、次の失敗とする。
  - 資格情報ストアの失敗
  - 通信の失敗
  - 上記2種類の OAuth エラー以外の更新エラー
  - 対象リポジトリの権限不足
- Device Flow へ進まない認証エラーでは、アプリケーションは理由を表示する。
- Device Flow へ進まない認証エラーでは、アプリケーションは失敗終了する。
- 更新時の失敗では、エラーに `GitHub token refresh failed` を付ける。
- Device Flow の認証失敗では、`GitHub device authorization failed` を付ける。
- 認証段階の表示には、秘密値を含めない。
- トークン更新が必要な場合、アプリケーションは `GITHUB_CLIENT_ID` を取得する。
- Device Flow が必要な場合も、アプリケーションは `GITHUB_CLIENT_ID` を取得する。
- 更新と Device Flow が不要な場合、アプリケーションは `GITHUB_CLIENT_ID` を取得しない。
- クライアント ID が未設定または空の場合、アプリケーションは失敗終了する。

### Device Flow の処理

1. アプリケーションは、デバイスコード取得へリクエストを送る。
2. アプリケーションは、応答から次の値を取得する。
   - `device_code`
   - `user_code`
   - `verification_uri`
   - `expires_in`
   - `interval`
3. アプリケーションは、`verification_uri` を表示する。
4. アプリケーションは、`user_code` を表示する。
5. アプリケーションは、ブラウザを自動起動しない。
6. アプリケーションは、`interval` 以上の間隔でトークン取得・更新をポーリングする。
7. `authorization_pending` の場合、アプリケーションは待機を継続する。
8. `slow_down` の場合、アプリケーションは GitHub の指示どおり待機間隔を延長する。
9. 認証が成功した場合だけ、アプリケーションはアクセストークンを資格情報ストアへ保存する。
10. 認証成功後、アプリケーションは発行済みリフレッシュトークンを資格情報ストアへ保存する。
11. 保存成功後、アプリケーションは Issue 取得を続ける。

- Device Flow のエラーは、次の失敗とする。
  - 認証の拒否
  - 認証の期限切れ
  - クライアント ID の不正
  - Device Flow の無効化
  - 通信の失敗
- Device Flow のエラーでは、アプリケーションは理由を表示する。
- Device Flow のエラーでは、アプリケーションは失敗終了する。

## 取得と判定

### Issue の取得

- アプリケーションは、GitHub REST API の次のエンドポイントを使用する。

```text
GET /repos/{owner}/{repo}/issues
```

- リクエストのパラメーターは、次の値とする。
  - `state=open`
  - `sort=created`
  - `direction=desc`
- 応答項目が `pull_request` フィールドを持つ場合、アプリケーションは項目を除外する。
- 除外後の Issue が 100 件に達するまで、アプリケーションは後続ページを読み取る。
- open Issue が 100 件未満の場合、アプリケーションは存在する件数だけを取得する。
- トリアージには、アプリケーションは `number`、`title`、`body` を使用する。
- `body: null` の場合、アプリケーションは本文なしとして扱う。
- 「最新」は、`created_at` の降順を意味する。

### Jev による重要度

- アプリケーションは、TypeSafe HTTP API の次のエンドポイントを使用する。

```text
POST https://api.typesafe.ai/v1/systemone
```

- アプリケーションは、次の認証ヘッダーを付ける。

```text
Authorization: Bearer <API_KEY>
```

- モデル名は、追従用エイリアス `jev-latest` とする。
- アプリケーションは、取得した最大100件の Issue を1つの構造化状態にまとめる。
- アプリケーションは、Issue ごとに独立した `Score` 質問を 1 つ作る。
- 判定指示には、対象 Issue の `number`、`title`、`body` のパスを明記する。
- 判定指示には、Issue の重要度を判定する目的を明記する。
- アプリケーションは、質問 ID の値自体に判定の意味を依存させない。
- `Score` の判定基準は、次の 5 段階を低い順に使用する。

| 段階 | 判定基準 |
| ---: | --- |
| 0 | 対応不要、情報提供のみ、または影響が確認できない |
| 1 | 影響が小さく、容易な回避策がある |
| 2 | 通常機能への影響はあるが、業務は継続できる |
| 3 | 主要機能の妨害、広いユーザーへの影響、または回避困難な問題 |
| 4 | データ損失、セキュリティ、サービス停止など、即時対応が必要な影響 |

- アプリケーションは、API が返す確率加重 `score` を検証する。
- アプリケーションは、検証済みの `score` を変換せず重要度として使用する。
- アプリケーションは、`confidence` を順位計算に使用しない。
- アプリケーションは `confidence` を表示しない。
- 次の失敗では、アプリケーションはコマンド全体を失敗させる。
  - 回答が一部でも欠落する。
  - 回答の型が不正である。
  - TypeSafe の処理が失敗する。
- アプリケーションは、回答の失敗を推測値で補わない。
- HTTP `429` または `529` の場合、アプリケーションは上限付き指数バックオフで再試行する。
- 再試行が上限に達した場合、アプリケーションは失敗終了する。
- 実装者は、再試行回数をテスト可能な定数として定める。
- 実装者は、タイムアウトをテスト可能な定数として定める。

### Jev の入力と出力

- アプリケーションは、Issue の構造化状態を Ready に使用する。
- アプリケーションは、1回の Jev リクエストを Ready に使用する。
- アプリケーションは、Issue ごとに独立した Ready の `Choice` 質問を 1 つ作成する。
- Jev は、重要度の `Score` 結果を Ready の判定材料に使用しない。
- Jev は、ブランチ分類の `Choice` 結果を Ready の判定材料に使用しない。
- 判定指示には、対象 Issue の `number`、`title`、`body` のパスを明記する。
- Jev は、次の 4 観点を評価する。
  - 具体的な振る舞いや問題を把握できるか
  - 要求の骨格を創作せず整理できるか
  - 仕様整理の開始を妨げる情報不足があるか
  - 仕様整理の開始前に事実調査が不可欠か
- Ready の選択肢は、次の3つとする。
  - `Yes`
  - `Needs information`
  - `Needs investigation`
- アプリケーションは、検証済みの選択結果を変換せず表示する。
- アプリケーションは、4観点を個別の回答として要求しない。
- アプリケーションは、4観点を追加列として表示しない。
- Jev は、タイトルと本文に記載された情報だけで Ready を判定する。
- Jev は、`brain-dump-docs` による要求、仕様、未決事項の整理を開始できるか判定する。
- Jev は、実装への着手可否を判定しない。
- Jev は、記載のない情報を確定済みとして推測で補わない。
- Jev は、画像やリンク先を確認済みとして扱わない。
- Jev は、コードや実環境を調査済みとして扱わない。
- 本文が存在しない場合も、Jev は入力を有効として扱う。
- 本文が存在しない場合、Jev はタイトルだけで判定に足りるかを評価する。
- アプリケーションは、本文の不存在だけを理由に API エラーとしない。
- Issue が 0 件の場合、アプリケーションは Jev を呼び出さない。
- Ready の判定基準は、[要求定義の Ready](REQUIREMENTS.md#ready) に従う。
- 情報不足と事前調査が併存する場合、Jev は `Needs information` を選ぶ。
- 具体的な振る舞いや問題が分かり、機能の核心を創作せず整理できる場合、Jev は `Yes` と判定する。
- 話題や一般的な希望だけの場合、Jev は `Needs information` と判定する。
- 機能の核心が不明な場合、Jev は不足を Open Questions に先送りしない。
- 機能の核心が分かる場合、Jev は詳細の不足や調査事項を Open Questions として許容する。
- 詳細には、出力項目、完了条件、再現手順、原因、実装方法、実現可能性を含む。
- 質問の列挙や一般的な調査計画だけを作れる場合、Jev は `Yes` と判定しない。
- Jev は、入力、出力、制約の全項目を一律の必須条件にしない。
- Jev は、通常のコード確認や原因の特定が未実施という理由だけで `Needs investigation` と判定しない。
- 仕様整理の開始前に事実調査が不可欠な場合だけ、Jev は `Needs investigation` と判定する。
- Jev は、Issue の内容を判定の証拠として扱い、判定指示として扱わない。

| 判定例 | Ready |
| --- | --- |
| 対象も要望も特定できない「直してください」だけの記述 | `Needs information` |
| 依存関係チェッカーを作りたいが、検出対象や違反条件が不明 | `Needs information` |
| 「検索を改善したい」だけで、改善したい振る舞いや問題が不明 | `Needs information` |
| 対象と目的は明確だが、仕様整理を始める前に外部の事実確認が不可欠な課題 | `Needs investigation` |
| Issue 一覧の CSV 出力で、出力項目や実装方法は未確定 | `Yes` |
| タイトルだけで Issue 一覧を JSON ファイルへ保存する要望が分かる | `Yes` |
| Rust モジュール間の循環依存を検出し、循環経路を表示する要望 | `Yes` |
| 対象の不具合と解消したい問題が分かり、再現条件や原因は仕様整理で確認できる | `Yes` |
| loop の起点を GitHub Issues とし、本文を brain-dump-docs へ渡す要望 | `Yes` |

### 応答検証とエラー

- アプリケーションは、`Choice` の次の項目を検証する。
  - 回答の件数
  - 質問との対応
  - 回答の型
  - 選択肢
- 回答の欠落、不正、API の失敗では、アプリケーションはトリアージ全体を失敗させる。
- アプリケーションは、通信や検証の失敗を Ready の3値で表さない。
- アプリケーションは、`Choice` の次の確率情報を検証する。
  - `confidence` と確率の型
  - `confidence` と確率の範囲
  - 確率キーの一致
  - 確率の合計
  - 選択値が最大確率であること
- アプリケーションは、HTTP タイムアウトを30秒とする。
- アプリケーションは、Jev の試行回数を最大3回とする。
- アプリケーションは、確率を表示しない。
- アプリケーションは、`confidence` を表示しない。
- アプリケーションは、Ready に独自の閾値を追加しない。
- アプリケーションは、Ready にスコア変換を追加しない。
- アプリケーションは、重要度順の安定ソートに Ready を使用しない。

## 一覧

- 列順は、重要度、Ready、番号、Author、Assignees、日付、Issues とする。
- Issues 列にはタイトルだけを表示する。
- 本文、ブランチ候補名、作成ボタンは一覧に表示しない。
- 各セルは上寄せ、左寄せとする。
- 内部の縦罫線の左右には、半角空白を1文字ずつ置く。
- テーブル幅は端末幅に合わせ、Unicode 表示幅で計算する。
- 長いタイトル、Author、Assignees はセル内で折り返す。
- 行の高さは、各セルの内容に必要な高さとする。
- 行高の上限とセル内スクロールは設けない。
- 一覧全体は、ホイール1イベントにつき1行移動する。
- 一覧の移動は先頭と末尾で停止する。
- ホイール操作で、仮選択を解除する。
- マウスオーバーで、対象行の各セルを青色背景にする。
- 仮選択では、罫線と他の行の表示を変更しない。
- 対象行の左クリックで、対象 Issue の本文ダイアログを開く。
- 罫線と一覧外のクリックでは、本文を開かない。
- 重要度の説明とブランチ確認不能理由は、一覧に表示する。
- 下部の最終行には、`HELP`、`QUIT`、`SEARCH` を順に配置する。
- 各ボタンは、左右各3文字の余白を含めて反転表示する。
- ボタン間には、反転しない半角空白を1文字置く。
- 各ボタンの左右の余白も、クリック対象とする。

| 一覧の操作 | 動作 |
| --- | --- |
| `HELP` または `h` | ヘルプダイアログを開く |
| `QUIT` または `q` | 端末状態を復元して終了する |
| `SEARCH` または `s` | 検索ダイアログを開く |
| マウスホイール | 一覧全体を上下に移動する |
| ソート対象の見出しのクリック | 列と方向を切り替える |
| Issue 行のクリック | 本文ダイアログを開く |

`h`、`q`、`s` のショートカットは、一覧だけで受け付ける。
Ctrl+C は、ダイアログ中も端末状態を復元して終了する。
一覧の操作キーは、`h`、`q`、`s`、Ctrl+C に限定する。

### 列の値とソート

- Author は GitHub の login とする。欠損値は `-` とする。
- Assignees は、全員の login を昇順に並べて `,` で連結する。
- Assignees が空の場合、`-` を表示する。
- 日付は、作成日時を JST の `YYYY-MM-DD` で表示する。
- 日付の比較には、作成日時全体を使用する。
- ソート対象は、重要度、番号、Author、日付とする。
- 初期状態は、重要度降順とする。
- 現在の列をクリックすると、方向を反転する。
- 別の列をクリックすると、対象列の昇順へ切り替える。
- 選択中の列には、昇順 `↑` または降順 `↓` を付ける。
- 見出しの余白はクリック対象とし、罫線は対象外とする。
- Author は、大文字と小文字を区別して比較する。
- Author の欠損は、両方向とも末尾へ置く。
- 同値の場合、GitHub の取得順を維持する。
- 並べ替え後は、仮選択を解除し、一覧の位置を維持する。
- 一覧の位置は、再描画後の移動可能範囲に補正する。
- 検索の実行と解除では、ソート列と方向を維持する。
- 見出しは、一覧と一緒にスクロールする。

## ダイアログ

### 共通

- ダイアログは、一覧の上に中央配置する。
- 外枠を含む横幅は、`floor(端末幅 * 3 / 4)` とする。
- 本文とヘルプの高さは、外枠込みで `端末の高さ - 4` 行とする。
- 内容は、外枠と左右の余白を除く幅で折り返す。
- 長文は、内容領域上のホイールで1行ずつ上下に移動する。
- 内容の移動は先頭と末尾で停止する。
- 見出しと下部ボタンは、内容と一緒に移動しない。
- `Close` ボタンのクリックで、一覧へ戻る。
- ダイアログの操作を、背後の一覧へ渡さない。
- Enter、Esc、矢印、PageUp、PageDown は操作を実行しない。
- 閲覧から戻る場合、一覧の検索、ソート、仮選択、位置を維持する。
- 描画できない寸法の場合、理由を示して終了する。

### 検索

- 高さは、上下の外枠を含めて7行に固定する。
- 内側は、タイトル、空行、入力欄と Search、空行、Close の 5 行とする。
- 検索入力欄は、検索ダイアログ内だけに表示する。
- 開いた直後から、文字入力と貼り付けを受け付ける。
- 入力欄は1行とし、長い検索語は末尾側を表示する。
- 入力欄の角括弧は太字にし、入力位置にカーソルを表示する。
- 空欄には、灰色の `Type keywords...` を表示する。
- 入力欄と同じ行に、反転表示の `Search` を配置する。
- `Search` の左右の余白も、クリック対象とする。
- `Search` をクリックすると、検索を確定してダイアログを閉じる。
- Enter では、検索を確定しない。
- `Close` のクリックでは、未確定の入力を破棄する。
- 次に開く場合、適用済みの検索語を入力欄へ戻す。
- 検索対象は、取得済みの最大 100 件のタイトルと本文とする。
- 語は Unicode の空白で区切り、すべての語の部分一致を要求する。
- 語順は不問とし、各語はタイトルと本文に分散してもよい。
- ASCII 英字の大文字と小文字は区別しない。
- 空文字と空白だけの検索では、取得済み全件へ戻す。
- 検索では、追加の API 呼び出しを行わない。
- 検索後は、一覧の仮選択を解除して先頭へ移動する。
- 該当なしでは、`No matching issues.` と表示する。
- 該当なしでも、検索ダイアログを再度開ける。
- 入力文字の `h`、`q`、`s` は、一覧操作へ渡さない。
- Backspace は、末尾の Unicode 文字を削除する。
- UTF-8 の分割受信は、文字の完成後に入力へ反映する。
- 不正または未完の UTF-8 を、別の文字へ置き換えない。
- 貼り付けの改行と Tab は、半角空白へ置き換える。
- 貼り付け中のキーや制御列は、アプリ操作を実行しない。
- IME の確定に、時間差による Enter 抑制を導入しない。

### Issue 本文とブランチ作成

- 行クリックで、同じ Issue の番号、タイトル、本文を表示する。
- 見出しは1行とし、幅を超える部分は表示しない。
- 本文の後に、ブランチ名の候補を表示する。
- 下部に、`Close` と `Create branch` を固定表示する。
- ボタンは反転表示し、左右の余白までクリック対象にする。
- `Create branch` は、表示中の Issue を作成対象にする。
- 検索とソートの後も、行、本文、作成対象を一致させる。
- 作成成功と失敗は、結果ダイアログへ表示する。
- 作成成功後は、一覧に戻る場合にブランチ状態を再確認する。
- 作成後も、検索条件、ソート、仮選択、位置を維持する。
- 作成失敗は成功として表示せず、失敗理由を表示する。

### ヘルプ

ヘルプは、現在の操作、検索、アイコン、重要度、Ready を説明する。
内容はホイールで閲覧し、`Close` で一覧へ戻る。

## ローカルブランチ

### Jev によるブランチ分類

- アプリケーションは、重要度判定とは独立した Jev の `Choice` 質問を使用する。
- 分類の質問は、同じ Issue の `number`、`title`、`body` を参照する。
- Jev は、次のブランチ分類のいずれかを選ぶ。
  - `refactor`
  - `fix`
  - `feat`
  - `chore`
  - `docs`
- アプリケーションは、最大100件という取得上限を維持する。
- アプリケーションは、重要度順を維持する。
- アプリケーションは、`Choice` の回答数と質問数の対応を検証する。
- アプリケーションは、`Choice` の型を検証する。
- アプリケーションは、`Choice` の選択肢を検証する。
- 回答が不完全または不正な場合、アプリケーションはトリアージを失敗させる。
- アプリケーションは、不完全または不正な回答を既定の `prefix` で置き換えない。
- アプリケーションは、Issue 番号を十進数で表す。
- ブランチ名は、`<prefix>/issue-<number>` とする。
- ブランチ名の作成には、アプリケーションはタイトルの翻訳を使用しない。
- ブランチ名の作成には、アプリケーションはタイトルの要約を使用しない。
- ブランチ名の作成には、アプリケーションは追加の生成 API を使用しない。

### プロジェクトルートの設定

ユーザーは、次のコマンドでプロジェクトルートを保存する。

```text
gh-issues-triage config set-root <directory>
```

- 保存対象は、既存ディレクトリの絶対パスとする。
- 設定ファイルの保存先は、次の規則に従う。

| 条件 | 保存先 |
| --- | --- |
| `XDG_CONFIG_HOME` が設定済み | `XDG_CONFIG_HOME/gh-issues-triage/config.json` |
| `XDG_CONFIG_HOME` が未設定 | `~/.config/gh-issues-triage/config.json` |

- 設定値は、秘密情報ではない公開パスとする。
- アプリケーションは、トークンを設定ファイルへ保存しない。
- アプリケーションは、API キーを設定ファイルへ保存しない。

### 作成と状態確認

- 対象ディレクトリは、保存済みの `root/repo` とする。
- 対象のパス、Git ルート、origin と指定リポジトリの一致を検証する。
- Git の引数は個別に渡し、シェル文字列へ埋め込まない。
- 作成名は、`<prefix>/issue-<number>` とする。
- 作成の起点は、対象ローカルリポジトリの `main` とする。
- `main` がない場合、別の ref を代用しない。
- 同名のブランチは上書きしない。
- 作成成功後は、新しいブランチへ切り替える。
- CLI 自身の作業ディレクトリは変更しない。
- 作成前には、ブランチの作成や切り替えを行わない。
- 状態確認は読み取り専用とし、`main` の存在を要求しない。
- 状態確認では、作成、切り替え、fetch、push を行わない。
- 許可済みの 5 分類の `refs/heads/<prefix>/issue-<number>` を照合する。
- Issue 番号は、先頭ゼロのない十進表記で完全一致させる。
- Jev が対象 Issue に返した分類と異なる許可 prefix も、照合対象に含める。
- 独自名とリモートのブランチは、照合対象に含めない。
- 番号列の `🌿` は存在、空欄は不存在、`?` は確認不能を示す。
- root 未設定、対象不一致、読み取り失敗は、確認不能として扱う。
- 確認不能の理由は一覧の下部に表示する。
- 状態確認だけの失敗では、一覧の表示を継続する。
- 外部操作によるブランチ変更と削除履歴は追跡しない。

## next の JSON 出力

### 取得と選択

1. アプリケーションは、本書の認証方式で Issue を取得する。
2. アプリケーションは、プルリクエストを除外する。
3. アプリケーションは、最新の open 状態の Issue 最大 100 件を対象にする。
4. アプリケーションは、本書の Jev 判定で全対象を判定する。
5. アプリケーションは、全回答を本書の応答検証規則で検証する。
6. アプリケーションは、重要度順の安定ソートを使用する。
7. アプリケーションは、Ready が `Yes` の最初の1件を選ぶ。
8. アプリケーションは、選択結果を JSON で出力する。

- READY は GitHub のラベルや Projects の状態を意味しない。
- READY は、検証済みの `Readiness::Yes` を意味する。
- 同じ重要度の候補では、GitHub の取得順を維持する。
- 取得順は、`created_at` 降順に従う。
- 作成日時が同じ候補でも、GitHub の取得順を維持する。
- ブランチが存在する場合も、アプリケーションは候補から除外しない。
- 対象外の古い Issue を求めて、アプリケーションは取得を続けない。
- Issue が0件の場合、アプリケーションは Jev を呼び出さない。
- 全回答の検証が完了するまで、アプリケーションは結果を出力しない。

### JSON の出力契約

- 該当 Issue がある場合、アプリケーションは単一オブジェクトを返す。
- 出力項目は、次の表に限定する。

| キー | JSON 型 | 内容 |
| --- | --- | --- |
| `repository` | string | CLI で指定した `owner/repo` |
| `number` | number（整数） | GitHub の Issue 番号 |
| `title` | string | GitHub から取得したタイトル |
| `body` | string | Issue データが保持する本文 |
| `score` | number | 検証済みの重要度。範囲は `0` 以上 `4` 以下 |
| `readiness` | string | 仕様整理へ着手可能であることを示す `Yes` |
| `branch_name` | string | ブランチ名の候補1件 |

- `branch_name` は、`<prefix>/issue-<number>` の形式とする。
- `prefix` は、選択された Issue の検証済みブランチ分類とする。
- `number` は、選択された Issue の番号とする。
- 候補は、ブランチ作成機能と同じ命名規則で生成する。
- 候補の出力は、ブランチの存在や作成可否を保証しない。

- GitHub の本文が `null` の場合、取得処理は空文字へ変換する。
- `next` は、取得処理で変換した本文を空文字で出力する。
- GitHub の本文が空文字の場合も、`next` は空文字で出力する。
- `score` は、検証済みの値を丸めずに出力する。
- JSON のキー順は、出力契約の対象外とする。
- アプリケーションは、UTF-8 の単一行 JSON を出力する。
- アプリケーションは、出力末尾に改行を1つ付ける。
- アプリケーションは、タイトルと本文を端末表示用に加工しない。
- アプリケーションは、改行や制御文字を JSON の規則でエスケープする。
- 標準出力には、テーブル、ANSI 装飾、進捗、認証案内を含めない。

出力例:

```json
{"repository":"owner/repo","number":42,"title":"保存処理の修正","body":"再現条件と完了条件。","score":3.6,"readiness":"Yes","branch_name":"fix/issue-42"}
```

該当 Issue がない場合の出力:

```json
null
```

### 終了、エラー、副作用

| 条件 | 標準出力 | 標準エラー出力 | 終了コード |
| --- | --- | --- | --- |
| 該当 Issue あり | 単一 JSON オブジェクト | 認証案内がある場合は案内 | `0` |
| Issue が0件 | `null` | 認証案内がある場合は案内 | `0` |
| Ready が `Yes` の Issue が0件 | `null` | 認証案内がある場合は案内 | `0` |
| CLI 入力不正 | 出力なし | 理由と使い方 | `2` |
| 認証、取得、判定、シリアライズの失敗 | 出力なし | 原因 | `1` |
| 標準出力への書き込み失敗 | 途中出力が残る可能性あり | 原因 | `1` |

- 認証、秘密情報の保護、タイムアウトは、本書の各仕様に従う。
- API の再試行と応答検証は、本書の各仕様に従う。
- アプリケーションは、処理失敗を `null` で置き換えない。
- アプリケーションは、端末の対話モードへ入らない。
- アプリケーションは、端末幅を出力条件に使用しない。
- アプリケーションは、ローカルブランチの状態を確認しない。
- アプリケーションは、プロジェクトルートを読み込まない。
- アプリケーションは、ブランチを作成または切り替えない。
- アプリケーションは、GitHub の Issue を更新しない。
- 認証情報の保存と更新は、本書の認証方式に従って実行する。

## 外部境界とエラー

- HTTP タイムアウトは 30 秒とする。
- GitHub と Jev の応答は、利用前に型と必須項目を検証する。
- 一覧は、Author、Assignees、作成日時の型と日時を検証する。
- `next` は、一覧用の属性を新しい必須条件にしない。
- API、保存、端末、出力の失敗を、成功や推測値へ置き換えない。
- 表示内容の制御文字は、幅計算と描画の前に無害化する。
- JSON の文字列は、端末表示用に加工しない。
- 一覧の7列を描画できない幅では、理由を示して終了する。
- ダイアログの横幅は 30 文字以上、高さは 7 行以上を要求する。
- 検索ダイアログの横幅は 37 文字以上を要求する。
- ダイアログの横幅には、固定ボタンを収める幅も要求する。
- 終了とエラーでは、端末の入力・表示モードを復元する。
- 取得結果が 0 件の場合、空の一覧を表示して終了する。
- トークンと API キーは、エラー表示に含めない。
