## Goal

長時間未使用後も、ユーザーが Issue の取得を再開できるようにする。
ユーザーによる Keychain の手動削除を不要にする。
更新時の特定の拒否エラーから、コード入力による再認証へ進める。

## Scope

- 保存済み認証からの GitHub Issue 取得。
- GitHub の HTTP 401 後のトークン更新。
- Device Flow へ進む条件と認証エラーの区別。
- `src/main.rs` の再認証条件とエラーの文脈。
- 認証の復旧経路を確認する動作テスト。
- 認証に関係する要求、仕様、設計と `README.md` の更新。

## Non-goals

- TypeSafe Jev の認証と判定処理。
- Issue の選択、検索、表示、ブランチ作成の変更。
- PAT、平文ファイル、クライアントシークレットの導入。
- 新しい依存関係と汎用認証層の導入。
- 原因未確認のまま行う期限情報の保存と事前更新。
- 全認証エラーを Device Flow へ切り替える処理。
- 資格情報ストアの項目を事前に削除する処理。
- 無人での再認証とバックグラウンドでの定期更新。

## Required Behavior

### Issue の報告

- 長時間未使用後に、次のエラーが発生する。
  - `[client error](error: client credentials were rejected)`
- Issue は、認証情報の更新機構を求めている。
- 「約 8 時間」と「期限切れ情報の再利用」は、報告者の推測である。

### ユーザーからの追加情報 (2026-10-15)

- ユーザーは、コードを入力して認証を行ったと説明した。
- 「GitHub App の更新」は、Device Flow の再認証を指すと理解する。
- 再認証まで、同じエラーが継続した。
- ユーザーは、Keychain Access で保存項目を削除した。
- 削除した項目名は、`gh-issues-triage` だった。
- 保存項目の削除後、コード入力で再認証して復旧した。
- 再認証を必要とした原因は、未確定である。
- App の設定変更やクライアント ID の変更は、報告されていない。

### 変更前に確認した実装

- `src/main.rs` は、保存済みトークンで Issue を取得する。
- HTTP 401 の場合、既存処理はリフレッシュトークンで更新する。
- 更新成功後、既存処理は両トークンを保存する。
- 保存成功後、既存処理は Issue 取得を一度だけ再試行する。
- リフレッシュトークンの不在か `bad_refresh_token` で再認証へ進む。
- `src/auth.rs` は、報告文言を `incorrect_client_credentials` に対応させる。
- 更新と Device Flow は、同じ OAuth 応答解析を使用する。
- エラー文言だけでは、失敗した認証段階を判別できない。
- 更新時のクライアント ID は、`GITHUB_CLIENT_ID` から取得する。
- 保存済み認証情報には、発行元のクライアント ID が含まれない。
- 資格情報ストアの保存形式は、単一の JSON である。
- 保存形式は、JSONL ではない。
- 保存対象は、アクセストークンとリフレッシュトークンである。
- 現在の実装は、有効期限を保存しない。
- OAuth は、認証 SDK を使わず `reqwest` で実装している。
- 今回の調査では、報告された実環境の障害を再現していない。
- 今回の調査では、秘密値と Keychain の内容を取得していない。

### 外部仕様と仮説

- GitHub の期限付き user access token の有効期限は 8 時間である。
- 対応する refresh token の有効期限は 6 か月である。
- Device Flow で発行したトークンの更新に secret は不要である。
- GitHub は、クライアント情報の誤りを上記 OAuth エラーで示す。
- 有効な保存済みトークンの利用中は、環境変数の不整合が表面化しない可能性がある。
- 更新時に環境変数の不整合が表面化する可能性がある。
- 保存済みトークンと現在の App の不整合は、未確認の仮説である。
- 期限情報の追加だけで障害を解消できる根拠はない。

### 承認済みの復旧動作

- 保存済みトークンで HTTP 401 が返った場合、従来どおり更新する。
- 更新が成功した場合、従来どおり保存と再取得へ進む。
- 更新が次のいずれかを返した場合、Device Flow へ一度だけ進む。
  - `bad_refresh_token`: 既存の開始条件。
  - `incorrect_client_credentials`: 今回追加する開始条件。
- 後者は、トークンの失効と断定せず、復旧の試行として扱う。
- 後者では、更新時にクライアント情報が拒否された旨を示す。
- アプリケーションは、再認証が必要である旨を示す。
- 案内は、既存の認証案内と同じ出力先へ送る。
- ユーザーは、表示されたコードで再認証する。
- 再認証は、既存の待機間隔と有効期限に従う。
- 再認証が失敗した場合、アプリケーションは失敗終了する。
- 再認証自身の拒否エラーでは、再認証を繰り返さない。
- エラーは、更新中と Device Flow 中を区別できる文脈を持つ。
- 認証成功後、アプリケーションは新しい認証情報を保存する。
- 認証前に、アプリケーションは既存の保存項目を削除しない。
- 保存成功後、アプリケーションは Issue 取得を一度だけ再試行する。
- 通信、権限、保存の失敗では、再認証へ切り替えない。
- `next` も、既存仕様どおり認証が必要な場合はユーザー操作を待つ。
- `next` の認証案内とエラーは、標準エラー出力へ送る。
- 現在のクライアント ID 自体が不正な場合、復旧は保証できない。
- 既存文書の再認証条件は、本変更に合わせて更新する。

### 維持する受け入れ条件

- 有効な保存済みトークンでは、更新と再認証を行わない。
- HTTP 401 後の更新成功では、新しい両トークンを保存する。
- 保存成功後の再取得は、一度だけ行う。
- 再取得が HTTP 401 の場合、更新を繰り返さない。
- リフレッシュトークンがないか拒否された場合、既存条件で再認証する。
- クライアント情報の拒否を、トークンの失効と同一視しない。
- 通信、権限、保存の失敗では、成功扱いせず原因を示す。
- エラーとログには、秘密値を出力しない。
- 既存 JSON と旧形式のトークン単体を読み取れる。
- `next` の認証案内とエラーは、標準エラー出力へ送る。
- `next` の JSON 出力契約は、維持する。
