## CLI

アプリケーションは、次のコマンド形式を受け付ける。

```text
gh-issues-triage <owner>/<repo>
gh-issues-triage config set-root <absolute-directory>
gh-issues-triage --help
```

- `--help` 単独の場合、アプリケーションは次の情報を標準出力へ表示する。
  - Cargo パッケージのバージョン
  - 使い方
  - 各引数の説明
- `--help` 単独の場合、アプリケーションは終了コード `0` で終了する。
- 入力エラーの条件は、次のいずれかとする。
  - 引数が存在しない。
  - サブコマンドが未知である。
  - 引数を `<owner>/<repo>` として解釈できない。
- 入力エラーの場合、アプリケーションは使い方を標準エラー出力へ表示する。
- 入力エラーの場合、アプリケーションは終了コード `2` で終了する。
- アプリケーションは、空文字の `owner` を拒否する。
- アプリケーションは、空文字の `repo` を拒否する。
- アプリケーションは、余分なパス要素を拒否する。
- 処理が成功した場合、アプリケーションは終了コード `0` で終了する。
- 次の処理が失敗した場合、アプリケーションは非ゼロの終了コードで終了する。
  - 入力の処理
  - 認証
  - 通信
  - 応答の処理
  - 保存
  - 表示

## 認証

### エンドポイント

| 名称 | HTTP メソッドと URL |
| --- | --- |
| デバイスコード取得 | `POST https://github.com/login/device/code` |
| トークン取得・更新 | `POST https://github.com/login/oauth/access_token` |

### 保存済み認証情報の使用と更新

- 保存済みアクセストークンが有効な場合、アプリケーションはアクセストークンを使用する。
- 保存済みアクセストークンの用途は、Issue の取得とする。
- アプリケーションは、旧版が保存したアクセストークン単体の値も読み取る。
- 次の条件を両方満たす場合、アプリケーションはトークン取得・更新へ更新要求を送る。
  - アクセストークンが失効している。
  - 保存済みリフレッシュトークンが存在する。
- 更新要求のパラメーターは、次の値とする。
  - `client_id`
  - `grant_type=refresh_token`
  - `refresh_token`
- Device Flow のトークン更新では、アプリケーションはクライアントシークレットを使用しない。
- 更新成功後、アプリケーションは2つのトークンを組として資格情報ストアへ保存する。
- 保存成功後、アプリケーションは新しいアクセストークンで Issue 取得を再試行する。

### Device Flow の開始条件

- 次の条件のいずれかを満たす場合だけ、アプリケーションは Device Flow を開始する。
  - アプリケーションの認証情報が未保存である。
  - アプリケーションのリフレッシュトークンが存在しない。
  - GitHub が `bad_refresh_token` を返す。
- Device Flow へ進まない認証エラーは、次の失敗とする。
  - 資格情報ストアの失敗
  - 通信の失敗
  - `bad_refresh_token` 以外の更新エラー
  - 対象リポジトリの権限不足
- Device Flow へ進まない認証エラーでは、アプリケーションは理由を表示する。
- Device Flow へ進まない認証エラーでは、アプリケーションは失敗終了する。
- トークン更新が必要な場合、アプリケーションは `GITHUB_CLIENT_ID` を取得する。
- Device Flow が必要な場合も、アプリケーションは `GITHUB_CLIENT_ID` を取得する。
- 更新と Device Flow が不要な場合、アプリケーションは `GITHUB_CLIENT_ID` を取得しない。
- クライアント ID が未設定または空の場合、アプリケーションは失敗終了する。

### Device Flow の処理

1. アプリケーションは、デバイスコード取得へリクエストを送る。
2. アプリケーションは、応答から次の値を取得する。
   - `device_code`
   - `user_code`
   - `verification_uri`
   - `expires_in`
   - `interval`
3. アプリケーションは、`verification_uri` を表示する。
4. アプリケーションは、`user_code` を表示する。
5. アプリケーションは、ブラウザを自動起動しない。
6. アプリケーションは、`interval` 以上の間隔でトークン取得・更新をポーリングする。
7. `authorization_pending` の場合、アプリケーションは待機を継続する。
8. `slow_down` の場合、アプリケーションは GitHub の指示どおり待機間隔を延長する。
9. 認証が成功した場合だけ、アプリケーションはアクセストークンを資格情報ストアへ保存する。
10. 認証成功後、アプリケーションは発行済みリフレッシュトークンを資格情報ストアへ保存する。
11. 保存成功後、アプリケーションは Issue 取得を続ける。

- Device Flow のエラーは、次の失敗とする。
  - 認証の拒否
  - 認証の期限切れ
  - クライアント ID の不正
  - Device Flow の無効化
  - 通信の失敗
- Device Flow のエラーでは、アプリケーションは理由を表示する。
- Device Flow のエラーでは、アプリケーションは失敗終了する。

## `<owner>/<repo>`

### Issue の取得

- アプリケーションは、GitHub REST API の次のエンドポイントを使用する。

```text
GET /repos/{owner}/{repo}/issues
```

- リクエストのパラメーターは、次の値とする。
  - `state=open`
  - `sort=created`
  - `direction=desc`
- 応答項目が `pull_request` フィールドを持つ場合、アプリケーションは項目を除外する。
- 除外後の Issue が10件に達するまで、アプリケーションは後続ページを読み取る。
- open 状態の Issue が10件未満の場合、アプリケーションは存在する件数だけを取得する。
- トリアージには、アプリケーションは `number`、`title`、`body` を使用する。
- `body: null` の場合、アプリケーションは本文なしとして扱う。
- 「最新」は、`created_at` の降順を意味する。

### Jev による重要度

- アプリケーションは、TypeSafe HTTP API の次のエンドポイントを使用する。

```text
POST https://api.typesafe.ai/v1/systemone
```

- アプリケーションは、次の認証ヘッダーを付ける。

```text
Authorization: Bearer <API_KEY>
```

- モデル名は、追従用エイリアス `jev-latest` とする。
- アプリケーションは、取得した最大10件の Issue を1つの構造化状態にまとめる。
- アプリケーションは、Issue ごとに独立した `Score` 質問を1つ作る。
- 判定指示には、対象 Issue の `number`、`title`、`body` のパスを明記する。
- 判定指示には、Issue の重要度を判定する目的を明記する。
- アプリケーションは、質問 ID の値自体に判定の意味を依存させない。
- `Score` の判定基準は、次の5段階を低い順に使用する。

| 段階 | 判定基準 |
| ---: | --- |
| 0 | 対応不要、情報提供のみ、または影響が確認できない |
| 1 | 影響が小さく、容易な回避策がある |
| 2 | 通常機能への影響はあるが、業務は継続できる |
| 3 | 主要機能の妨害、広いユーザーへの影響、または回避困難な問題 |
| 4 | データ損失、セキュリティ、サービス停止など、即時対応が必要な影響 |

- アプリケーションは、API が返す確率加重 `score` を検証する。
- アプリケーションは、検証済みの `score` を変換せず重要度として使用する。
- アプリケーションは、`confidence` を順位計算に使用しない。
- 初期版では、アプリケーションは `confidence` を表示しない。
- 次の失敗では、アプリケーションはコマンド全体を失敗させる。
  - 回答が一部でも欠落する。
  - 回答の型が不正である。
  - TypeSafe の処理が失敗する。
- アプリケーションは、回答の失敗を推測値で補わない。
- HTTP `429` または `529` の場合、アプリケーションは上限付き指数バックオフで再試行する。
- 再試行が上限に達した場合、アプリケーションは失敗終了する。
- 実装者は、再試行回数をテスト可能な定数として定める。
- 実装者は、タイムアウトをテスト可能な定数として定める。

### 並べ替え

- アプリケーションは、重要度の降順で Issue を安定ソートする。
- 重要度が同じ場合、アプリケーションは GitHub から取得した順序を維持する。

- アプリケーションは、`Issues` 列にタイトルを表示する。
- アプリケーションは、タイトル直後の行から本文を表示する。
- アプリケーションは、入力中の改行を保持する。
- アプリケーションは、各行を列幅で折り返す。

### 一覧の仮選択とスクロール

- マウスが Issue 上にある場合、アプリケーションは Issue を仮選択する。
- マウスが Issue の行範囲外へ移動した場合、アプリケーションは仮選択を解除する。
- ヘッダー、横罫線、ヘルプは、Issue の行範囲に含めない。
- `j` または下矢印の場合、アプリケーションは次の Issue を仮選択する。
- `k` または上矢印の場合、アプリケーションは前の Issue を仮選択する。
- 先頭または末尾に達した場合、アプリケーションは仮選択の移動を止める。
- アプリケーションは、先頭と末尾の間で仮選択を循環させない。
- 仮選択がない場合、アプリケーションは初回の仮選択キー操作で先頭の表示 Issue を選ぶ。
- Issue がまだ表示されていない場合、アプリケーションは一覧の先頭の Issue を選ぶ。
- アプリケーションは、最後のマウス移動または仮選択キー操作を優先する。
- マウスオーバー後のキー操作では、アプリケーションは仮選択中の Issue を移動の基準にする。
- 仮選択した Issue が画面外の場合、アプリケーションは一覧を自動スクロールする。
- Issue が画面より高い場合、アプリケーションは仮選択後に Issue の先頭を表示する。
- PageUp と PageDown では、アプリケーションは一覧を表示領域の行数分スクロールする。
- 上端または下端に達した場合、アプリケーションはスクロールを止める。
- PageUp と PageDown では、アプリケーションは仮選択を維持する。
- アプリケーションは、仮選択した Issue の全セルに次の色を適用する。
  - 背景: bright blue（SGR `104`）
  - 文字: black（SGR `30`）
- 色の適用対象は、余白、タイトル、本文、ブランチ作成ボタンを含む。
- アプリケーションは、ANSI 16色を使用する。
- 実際の色味は、端末のパレットに従う。
- 各縦罫線の直前で、アプリケーションは前景色と背景色を既定色へ戻す。
- アプリケーションは、外枠、縦罫線、横罫線、ヘッダー、ヘルプの色を変えない。
- アプリケーションは、仮選択だけでブランチを作成しない。
- 作成結果画面では、アプリケーションは `j`、`k`、上下矢印で作成結果を1行ずつスクロールする。

## 設定と秘密情報

- アプリケーションは、環境変数 `TYPESAFE_API_KEY` から API キーを取得する。
- アプリケーションは、TypeSafe の API キーを永続保存しない。
- アプリケーションは、環境変数 `GITHUB_CLIENT_ID` からクライアント ID を取得する。
- アプリケーションは、クライアントシークレットを使用しない。
- アプリケーションは、PAT を使用しない。
- アプリケーションは、アクセストークンを資格情報ストアへ保存する。
- リフレッシュトークンの発行後、アプリケーションはリフレッシュトークンを資格情報ストアへ保存する。
- 資格情報ストアの保存先識別子は、次の値とする。
  - サービス名: `gh-issues-triage`
  - アカウント名: `github.com`
- macOS では、アプリケーションは Keychain を使用する。
- Linux では、アプリケーションは Secret Service を使用する。
- 資格情報ストアを利用できない場合、アプリケーションは失敗終了する。
- アプリケーションは、資格情報ストアの代替手段として平文ファイルを使用しない。
- アプリケーションは、秘密情報をエラー本文へ含めない。

## 対象

- アプリケーションの対象サービスは、GitHub.com に限定する。
- アプリケーションの対応 OS は、macOS と Linux とする。
- 対象リポジトリは、GitHub App とユーザーの権限でアクセスできる範囲に限定する。
- 対象リポジトリは、公開リポジトリと非公開リポジトリを含む。

## 追加仕様: ブランチ作成

### Jev によるブランチ分類

- アプリケーションは、重要度判定とは独立した Jev の `Choice` 質問を使用する。
- 分類の質問は、同じ Issue の `number`、`title`、`body` を参照する。
- Jev は、次のブランチ分類のいずれかを選ぶ。
  - `refactor`
  - `fix`
  - `feat`
  - `chore`
  - `docs`
- アプリケーションは、最大10件という取得上限を維持する。
- アプリケーションは、重要度順を維持する。
- アプリケーションは、`Choice` の回答数と質問数の対応を検証する。
- アプリケーションは、`Choice` の型を検証する。
- アプリケーションは、`Choice` の選択肢を検証する。
- 回答が不完全または不正な場合、アプリケーションはトリアージを失敗させる。
- アプリケーションは、不完全または不正な回答を既定の `prefix` で置き換えない。
- アプリケーションは、Issue 番号を十進数で表す。
- ブランチ名は、`<prefix>/issue-<number>` とする。
- ブランチ名の作成には、アプリケーションはタイトルの翻訳を使用しない。
- ブランチ名の作成には、アプリケーションはタイトルの要約を使用しない。
- ブランチ名の作成には、アプリケーションは追加の生成 API を使用しない。

### プロジェクトルートの設定

ユーザーは、次のコマンドでプロジェクトルートを保存する。

```text
gh-issues-triage config set-root <directory>
```

- 保存対象は、既存ディレクトリの絶対パスとする。
- 設定ファイルの保存先は、次の規則に従う。

| 条件 | 保存先 |
| --- | --- |
| `XDG_CONFIG_HOME` が設定済み | `XDG_CONFIG_HOME/gh-issues-triage/config.json` |
| `XDG_CONFIG_HOME` が未設定 | `~/.config/gh-issues-triage/config.json` |

- 設定値は、秘密情報ではない公開パスとする。
- アプリケーションは、トークンを設定ファイルへ保存しない。
- アプリケーションは、API キーを設定ファイルへ保存しない。

### 対象の検証と作成操作

- アプリケーションは、CLI の `repo` をローカルディレクトリ名に使用する。
- 対象ローカルリポジトリは、`root/repo` とする。
- プロジェクトルートが未設定の場合、アプリケーションはブランチ作成を拒否する。
- 対象パスが存在しない場合、アプリケーションはブランチ作成を拒否する。
- Git 操作前に、アプリケーションは対象パスと対象リポジトリの対応を検証する。
- ブランチの起点は、対象ローカルリポジトリの `main` とする。
- `main` が存在しない場合、アプリケーションは別の ref を代用しない。
- 同名ブランチが存在する場合、アプリケーションはブランチを上書きしない。
- アプリケーションは、各 Issue の本文下にブランチ名を表示する。
- アプリケーションは、各 Issue の本文下にマウスでクリックできる作成ボタンを表示する。
- ボタンのクリック後、アプリケーションは対応するブランチを作成する。
- クリックを受け付ける間、アプリケーションは端末の対話状態を維持する。
- `1`〜`9` の入力では、アプリケーションは対応する Issue のブランチを作成する。
- `0` の入力では、アプリケーションは10件目の Issue のブランチを作成する。
- 作成後、アプリケーションは対象ローカルリポジトリを新しいブランチへ切り替える。
- アプリケーションは、CLI の作業ディレクトリを変更しない。
- アプリケーションは、Git 操作の対象ローカルリポジトリを明示する。
- アプリケーションは、クリック前にブランチを作成しない。
- ディレクトリ、Git、Jev のエラーでは、アプリケーションは理由を表示する。
- アプリケーションは、ディレクトリ、Git、Jev のエラーを成功表示しない。
- アプリケーションは、`repo` をシェル文字列へ直接埋め込まない。

ブランチ状態の表示は2026-10-01に実装済みである。
実端末でのブランチ状態の表示確認は未実施である。
照合範囲と確認方法は、承認済み表示の実装を補う仕様とする。

### 表示

- テーブルの列順は、`重要度`、`Ready`、`番号`、`Issues` とする。
- アプリケーションは、各 Issue の先頭行の番号右隣にブランチ状態を表示する。
- アプリケーションは、番号部分を番号の最大表示幅まで空白で埋める。
- アプリケーションは、番号部分の後ろに半角空白1文字を置く。
- アプリケーションは、半角空白の後ろにブランチ状態の領域を置く。
- アプリケーションは、全 Issue でブランチ状態の位置を揃える。
- ブランチ状態の記号は、次の対応とする。

| ブランチ状態 | 記号 |
| --- | --- |
| ブランチあり | `🌿` |
| ブランチなし | 空欄 |
| 確認不能 | `?` |

- 状態領域の幅は、`🌿` の Unicode 表示幅とする。
- アプリケーションは、空欄と `?` の余白を状態領域の幅に合わせる。
- アプリケーションは、番号列の幅にブランチ状態と左右の余白を含める。
- アプリケーションは、残りの幅を `Issues` 列へ割り当てる。
- 端末幅が不足する場合、アプリケーションはテーブルの幅不足仕様に従う。
- Issue が1件以上の場合、アプリケーションは一覧のヘルプに次の凡例を表示する。

```text
🌿 ブランチあり / 空欄 ブランチなし / ? 確認不能
```

- 凡例は、論理1行とする。
- 凡例が端末幅に収まらない場合、アプリケーションは既存の処理で凡例を折り返す。
- Issue が0件の場合、アプリケーションはヘッダーだけを表示する。
- アプリケーションは、ブランチ状態に番号セルと同じ仮選択ハイライトを適用する。
- アプリケーションは、凡例を Issue の仮選択領域に含めない。

### 照合と確認不能

- 一覧表示前に、アプリケーションは対象ローカルリポジトリを一度だけ解決する。
- 対象の解決には、アプリケーションは保存済みプロジェクトルートと CLI の `repo` を使用する。
- アプリケーションは、既存の対象検証規則で Git ルートを確認する。
- アプリケーションは、既存の対象検証規則で origin と対象リポジトリの一致を確認する。
- アプリケーションは、次の形式のローカルブランチを確認する。

```text
refs/heads/<prefix>/issue-<number>
```

- 照合する `prefix` は、許可済みの5つのブランチ分類に限定する。
- アプリケーションは、Issue 番号を完全一致で照合する。
- Jev の今回の分類と異なる許可 `prefix` でも、アプリケーションは照合対象に含める。
- 同じ Issue 番号のブランチが存在する場合、アプリケーションは `🌿` を表示する。
- アプリケーションは、次のブランチや ref を照合対象に含めない。
  - 独自命名のブランチ
  - リモート追跡 ref（remote-tracking ref）
  - リモート上だけのブランチ
- ブランチ状態は、確認した時点の存在状態を示す。
- アプリケーションは、削除済みブランチの作成履歴を追跡しない。
- アプリケーションは、一覧表示後の外部操作によるブランチ変更を追跡しない。
- 一覧からの作成が成功した場合、アプリケーションは一覧へ戻る前にブランチ状態を再確認する。
- 再確認後、アプリケーションは番号右隣の表示を更新する。
- 再確認後、アプリケーションは確認不能の理由を更新する。
- 一覧へ戻る場合、アプリケーションは仮選択を維持する。
- 一覧へ戻る場合、アプリケーションはスクロール位置を表示領域内に補正する。
- 存在確認では、アプリケーションは `main` の存在を要求しない。
- ブランチ作成では、アプリケーションは `main` の存在を検証する。
- 次の条件では、アプリケーションは確認不能の `?` を表示する。
  - プロジェクトルートが未設定である。
  - 設定の読み込みが失敗する。
  - 対象パスが存在しない。
  - 対象ローカルリポジトリが指定と一致しない。
  - Git による確認が失敗する。
- 確認不能の場合、アプリケーションは確認できなかった理由を表示する。
- 原因が共通の場合、アプリケーションは原因を1回だけ表示する。
- アプリケーションは、確認失敗をブランチなしとして扱わない。
- ブランチ状態の確認だけが失敗した場合、アプリケーションは一覧表示を継続する。
- ブランチ状態の確認だけが失敗した場合、アプリケーションは終了コードを失敗にしない。
- 次の失敗は、既存のエラー仕様に従う。
  - 認証
  - Issue の取得
  - Jev の判定
  - 端末表示
  - ブランチ作成
- アプリケーションは、ブランチ状態を読み取り専用で確認する。
- ブランチ状態の確認では、アプリケーションは作成、切り替え、fetch、push を実行しない。
- ブランチ状態の確認は、既存の作成対象名を変更しない。
- ブランチ状態の確認は、既存のボタンを変更しない。
- ブランチ状態の確認は、既存のキー操作を変更しない。
- ブランチ状態の確認は、既存の作成結果画面を変更しない。

## 追加仕様: 着手可能度（Ready）

### Jev の入力と出力

- アプリケーションは、既存の構造化状態を Ready に使用する。
- アプリケーションは、既存の1回の Jev リクエストを Ready に使用する。
- アプリケーションは、Issue ごとに独立した Ready の `Choice` 質問を1つ追加する。
- Jev は、重要度の `Score` 結果を Ready の判定材料に使用しない。
- Jev は、ブランチ分類の `Choice` 結果を Ready の判定材料に使用しない。
- 判定指示には、対象 Issue の `number`、`title`、`body` のパスを明記する。
- Jev は、次の4観点を評価する。
  - 要求の具体性
  - 必要な再現条件
  - 完了条件
  - 着手前の事前調査
- Ready の選択肢は、次の3つとする。
  - `Yes`
  - `Needs information`
  - `Needs investigation`
- アプリケーションは、検証済みの選択結果を変換せず表示する。
- アプリケーションは、4観点を個別の回答として要求しない。
- アプリケーションは、4観点を追加列として表示しない。
- Jev は、タイトルと本文に記載された情報だけで Ready を判定する。
- Jev は、記載のない再現条件を推測で補わない。
- Jev は、記載のない完了条件を推測で補わない。
- Jev は、コードや実環境を調査済みとして扱わない。
- 本文が存在しない場合も、Jev は入力を有効として扱う。
- 本文が存在しない場合、Jev はタイトルだけで判定に足りるかを評価する。
- アプリケーションは、本文の不存在だけを理由に API エラーとしない。
- Issue が0件の場合、アプリケーションは Jev を呼び出さない。
- Ready の判定基準は、[要求定義の判定基準](REQUIREMENTS.md#判定基準)に従う。
- 情報不足と事前調査が併存する場合、Jev は `Needs information` を選ぶ。
- 再現条件は、不具合など再現が必要な Issue に適用する。
- 次の Issue では、Jev は再現手順の不存在だけで `Needs information` と判定しない。
  - 機能追加の Issue
  - 文書変更の Issue
- 通常のコード確認だけで足りる場合、Jev は `Needs investigation` と判定しない。
- 通常の実装方法の選択だけで足りる場合、Jev は `Needs investigation` と判定しない。
- 原因が未特定の場合、Jev は着手前の事前調査が必要かを評価する。
- Jev は、原因が未特定という記述だけで一律に Ready を決めない。

| 判定例 | Ready |
| --- | --- |
| 期待する動作が不明な不具合 | `Needs information` |
| 再現条件と期待する動作が明確だが、原因の事前調査が必要な不具合 | `Needs investigation` |
| 変更内容と完了条件が具体的な文書修正 | `Yes` |

### 応答検証とエラー

- アプリケーションは、既存の `Choice` と同じ規則で次の項目を検証する。
  - 回答の件数
  - 質問との対応
  - 回答の型
  - 選択肢
- 回答の欠落、不正、API の失敗では、アプリケーションはトリアージ全体を失敗させる。
- アプリケーションは、通信や検証の失敗を Ready の3値で表さない。
- アプリケーションは、既存の `Choice` と同じ規則で次の確率情報を検証する。
  - `confidence` と確率の型
  - `confidence` と確率の範囲
  - 確率キーの一致
  - 確率の合計
  - 選択値が最大確率であること
- アプリケーションは、既存の HTTP タイムアウトを維持する。
- アプリケーションは、既存の上限付き再試行を維持する。
- アプリケーションは、確率を表示しない。
- アプリケーションは、`confidence` を表示しない。
- アプリケーションは、Ready に独自の閾値を追加しない。
- アプリケーションは、Ready にスコア変換を追加しない。
- アプリケーションは、重要度順の安定ソートに Ready を使用しない。

### テーブルと操作

- アプリケーションは、既存の3列を4列へ変更する。
- テーブルの列順は、`重要度`、`Ready`、`番号`、`Issues` とする。
- アプリケーションは、番号右隣のブランチ状態を維持する。
- アプリケーションは、Ready を上寄せにする。
- アプリケーションは、Ready を左寄せにする。
- アプリケーションは、各 Issue の先頭行に Ready の値全体を表示する。
- アプリケーションは、各 Issue の後続行の Ready セルを空欄にする。
- アプリケーションは、Ready の値を省略または略記しない。
- Ready 列の内容幅は、ヘッダーと一覧内の判定文字列の最大 Unicode 表示幅とする。
- アプリケーションは、Ready 列の左右の余白に既存の列と同じ規則を適用する。
- アプリケーションは、残りの幅を `Issues` 列へ割り当てる。
- 4列と `Issues` の最小幅を確保できない場合、アプリケーションは幅不足の理由を示す。
- 幅不足の場合、アプリケーションは既存の幅不足エラーとして失敗終了する。
- Issue が0件の場合も、アプリケーションは Ready を含むヘッダーだけを表示する。
- アプリケーションは、Ready の値と余白に既存の仮選択ハイライトを適用する。
- アプリケーションは、Ready の追加で罫線を装飾しない。
- アプリケーションは、列追加後のクリック領域を描画結果に合わせる。
- アプリケーションは、列追加後の Issue の物理行範囲を描画結果に合わせる。
- Ready は、ユーザー向けの参照情報とする。
- アプリケーションは、Ready の値を理由にブランチ作成を禁止しない。
- アプリケーションは、Ready の値を理由に追加確認を要求しない。
- アプリケーションは、Ready の判定結果を永続保存しない。
- アプリケーションは、一覧内で Ready を再判定しない。
- アプリケーションは、Ready のポーリングを追加しない。
